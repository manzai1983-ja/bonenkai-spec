1. 概要

LINEグループに「忘年会幹事」Bot（LINE公式アカウント）を招待しておくと、毎年決まった日に自動で次のことを行う。

  • 出欠の募集（候補日 12/27〜12/30）と集計、開催日の決定
  • 藤沢駅周辺の「鍋コース・飲み放題付き・6,000円以内・ネット予約可」のお店を探し、候補3店で投票
  • 投票結果と空席を確認してお店を決定し、幹事に予約リンクをメール

出欠と投票は、LINEに貼られるリンク先のWebページ（調整さん風）で入力する。入力してもLINEのトークには何も流れない。

開始時刻は毎年 18:00。どの候補日も出席が 3人以下 ならその年は中止。

2. 年間スケジュール

毎朝9時台に自動実行（トリガー dailyJob）し、日付に応じて処理する。実行が遅れても締切内であれば次の日に追いつく。

日付処理送り先
11/22下調べ：条件に合う店をGoogle・ホットペッパーの平均評価順に10店リストアップし、食べログの点数入力ページを案内幹事（LINE・メール）
11/23出欠募集：候補日と「出欠を入力する」ボタンを投稿送信先グループ
第1土曜の前日まで出欠を受付（何度でも修正可）／幹事は食べログの点数を入力―
12月第1土曜集計・開催日決定：最多の日に決定（3人以下なら中止を連絡）。候補3店を投票ボタン付きで投稿送信先グループ
翌週の日曜まで投票を受付（開催日に出席の人だけ）―
翌週の月曜お店決定：投票結果と空席を確認して決定・投稿。幹事に予約リンク付きメール送信先グループ＋幹事メール

2026年の例：11/22 下調べ → 11/23 出欠募集 → 12/4(金) 出欠締切 → 12/5(土) 開催日決定・投票開始 → 12/13(日) 投票締切 → 12/14(月) お店決定。

3. 開催日・お店の決め方

開催日

  • 12/27〜12/30 のうち「出席」の人数が最も多い日。同数なら早い日。
  • 最多の日でも出席が3人以下なら中止。

投票の候補（3店）

① 下調べ10店Google＋ホットペッパーの平均評価が高い順の上位10店（11/22）
② 食べログ順に並べ替え幹事が入力した食べログの点数が高い順。未入力の店は後ろ
③ 空席確認開催日・18時・出席人数で、ホットペッパーのネット予約に空きがある店だけ
④ 上位3店即予約できる店（◎○△）を優先し、リクエスト予約（□）は後回し。足りなければ11位以下から補う

お店の決定

  • 票の多い順。同じ票数・投票なしの場合は食べログの点数が高い店（次に平均評価）。
  • 投票できるのは開催日に「出席」の人だけ。出席者以外の票は数えない。
  • 決定時にもう一度空席を確認し、満席なら次の順位の店に繰り下げ（理由を投稿に記載）。全店満席なら幹事が手配する旨を投稿。

4. お店探しの仕組み

段階内容データ元
範囲JR藤沢駅から1km以内、飲み放題あり・コースありの全店（約170店）ホットペッパーAPI
コース条件「鍋あり」の印（または名前に鍋・しゃぶ・すき焼）×「飲み放題」×税込6,000円以下。条件内で最も高いコースを採用ホットペッパーのコースページ
予約ネット予約に対応している店だけホットペッパーの店ページ
口コミ数Googleの口コミが100件以上Google Places API (New)

食べログ幹事が入力ページで手入力。最終候補3店の順位と同票時の決め手に使う手入力（自動取得はしない）
空席開催日・18:00・人数でのネット予約カレンダー（◎○△□×休）ホットペッパーの予約カレンダー

食べログは利用規約でプログラムによる取得・保存が禁止されているため、点数は自動で取らない。各ページに「食べログで見る」検索リンクだけを付ける（店名が食べログと違う店は直リンクを手動登録）。

5. 画面（Webページ）

出欠表ページ（参加者向け）LINEの「出欠を入力する」から

  • 上段：全員の出欠表（名前・日付ごとの出席／欠席・コメント・出席人数。最多の日を強調）
  • 下段：入力欄（名前・日ごとの「出席」「欠席」・コメント）。表の名前を押すとその人の回答を修正・削除できる
  • 開催日決定後：入力欄は締め切り。上に開催日・出席者・投票状況（順位・票数・誰が投票したか）と投票欄（名前を選んでお店を選ぶ）を表示
  • 各店に「コースを見る」「食べログで見る」リンク、評価（食べログ・Google・ホットペッパー）、価格、空き状況

食べログの点数入力ページ（幹事向け）11/22の下調べ通知から

  • 下調べ10店の一覧。各店の「食べログで見る」で点数を確認し、1.00〜5.00で入力して保存
  • 今の点数で上位3店に色が付く。開催日決定後は入力不可

7. 送信先グループ

種類役割現在
送信先グループ出欠募集・開催決定・お店決定を送る本番のグループ本番グループ
保留中のグループ招待されたが、まだ送信先にしていないグループ―
Botを新しいグループに招待しても送信先は自動では変わらず、「保留中」に記録されるだけ。送信先の切り替えは幹事の管理操作でのみ行う（誤招待・なりすまし対策）。

8. システム構成

部品内容
Google Apps Script本体。Webアプリ（出欠表・食べログ入力ページ、LINE Webhook）と毎朝のトリガー。所有者のGoogleアカウントで動作
LINE公式アカウント「忘年会幹事」Messaging API（無料のコミュニケーションプラン、月200通）。チャネルIDとシークレットから都度15分の短期トークンを発行して送信
Googleスプレッドシート「忘年会幹事Bot_記録」：出欠・コメント・投票・候補店・ログ
Google CloudPlaces API (New) 用。Places専用に制限したAPIキー、1日100回の上限、予算100円のアラート
ホットペッパーグルメAPI店の検索（無料）。コース・評点・空席は店のWebページから読み取り

9. データの保存先

保存先中身
スクリプトプロパティ（非公開）各種APIキー、Webhook鍵、ページの鍵、送信先・保留中グループ、年ごとの状態（STATE_年：募集済み・決定日・候補店・決定店など）、下調べ10店と食べログの点数（PRE_年）
スプレッドシート「出欠」年・日付・名前・回答（○／×）・更新日時
スプレッドシート「コメント」「投票」「候補店」「ログ」コメント、投票（年・名前・候補番号・店名）、候補店の記録、処理ログ
キャッシュ（6時間）Googleの評価（API回数の節約）、LINEの短期トークン

スプレッドシートは所有者のGoogleドライブにあり共有していない。出欠・投票は名前で記録し、LINEのユーザーIDは保存しない。

10. セキュリティ

実装済みの対策

対象対策
キー類コード・ページ・スプレッドシートに置かない。スクリプトプロパティにのみ保存。GoogleのキーはPlaces API専用・日次上限つき
出欠表・投票ページURLにランダムな鍵（16桁）が必要。サーバー側で入力を検証（名前20文字・コメント100文字・出欠は2択・点数は1〜5）。表示時に必ずエスケープ（XSS対策）。締切後の変更や出席者以外の投票は拒否。保存は排他ロック
食べログ入力ページ別の鍵（16桁）。リンクは幹事にだけ送る
LINE WebhookGASはLINEの署名ヘッダーを読めないため、①URLの秘密鍵（暗号用乱数256bit）②宛先が自分のBotかの確認 ③送信先グループはイベントで変更しない ④参加イベントはLINEに実在確認してから保留に記録、の4段で防御

残っているリスク

リスク程度内容・対策案
なりすまし中名前だけで本人を区別するため、URLを知っていれば他人の出欠修正・削除・代理投票が可能（調整さんと同等）。対策案：最初に保存した端末だけが変更・削除できるようにする
大量登録低架空の名前を大量に保存できる。対策案：1年あたりの人数上限

11. 幹事の作業

  • 11/22〜第1土曜の前日：食べログの点数を入力（約5分）
  • お店決定の日：メールの予約リンク（日付・18:00・人数入り）から予約

12. 費用と外部サービス

サービス費用備考
Google Apps Script・スプレッドシート無料個人のGoogleアカウント
LINE Messaging API無料月200通まで。グループへの1投稿は人数分として数える
Google Places API (New)無料枠内（0円）1回の検索で約30回。日次上限100回・予算アラート100円
ホットペッパーグルメAPI無料クレジット表記の義務あり

13. 制約・既知の課題

  • 予約の確定は自動化しない（規約・誤予約のリスク）。幹事が予約リンクから確定する。
  • ホットペッパーのページ構成が変わると、コース・評点・空席の読み取りが失敗する可能性がある（空席が確認できない店は後回しにして続行）。
  • 「食べログで見る」は店名検索のため、名前が違う店はヒットしないことがある（直リンクを手動登録して対応）。
  • 「鍋あり」はホットペッパーの印に依存する。
